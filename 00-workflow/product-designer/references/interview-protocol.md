# 产品访谈协议

用途：规定怎样通过对话帮助用户想得更深，同时避免问卷化、无限追问和把 Agent 猜测伪装成用户决定。

## 1. 先吸收，后提问

每次开始或继续产品讨论时：

1. 读取已有 Product Definition。
2. 吸收用户本轮给出的新信息和所有明确想法。
3. 找出当前最值得继续理解的 1–3 个缺口。
4. 已经明确的信息不重复问。

如果用户一次给了很多内容，优先先做结构化反馈：指出你理解到的产品核心、最重要的新结论、明显矛盾和最值得深挖的少数问题，而不是立刻追加一长串问题。

## 2. 问题合法性测试

一个问题值得问，通常因为不同答案会改变至少一项：

1. 产品是什么、为谁存在。
2. 用户真正完成什么结果、闭环如何成立。
3. 角色、数据 / 内容 / 资产归属、权限或不可逆操作。
4. 谁获得价值、谁付费、免费 / 付费与持续付费逻辑。
5. 当前最小完整成果。
6. 重要市场或竞争假说。
7. 3–5 年产品模型和长期架构判断。

不能通过测试的问题，不占用核心访谈轮次。

## 3. 每轮问题纪律

- 通常每轮 1–3 问。
- 优先问当前最能改变整体判断的问题。
- 可以持续多轮，不设置机械的“最多两轮必须出稿”。
- 用户已经进入深入思考时，不要为了快而强行截断。
- 用户明显没时间时，减少提问，先给有依据的候选判断让用户修改。
- 一个问题能通过具体选项 + 后果帮助思考时，优于空泛开放题。

示例：

不优：`你希望产品支持怎样的协作？`

更优：`团队成员离开后，他创建的内容继续归团队，还是随个人离开？前者更适合组织资产，后者更强调个人所有权——你希望产品站哪一边？`

## 4. 深刻问题不是刁难

深刻问题要帮助用户看清真实取舍，而不是追求“难”。常用方向：

### 产品成立性

- 如果用户不用我们，他现在到底怎么解决？
- 为什么这件事值得用户改变原有行为？
- 这是一次不便，还是足以让用户行动的真实问题？

### 用户闭环

- 用户为什么在这个时刻进入？
- 第一次可感知价值多久出现？
- 哪一步最容易退出？
- 完成一次以后为什么还回来？

### 商业闭环

- 使用者和付款者是不是同一个人？不是的话，付款者得到什么？
- 用户持续付费的理由是持续价值还是迁移锁定？
- 规模扩大后收入增长和交付成本增长是什么关系？

### 市场现实

- 这个模式成立需要哪几个外部事实同时为真？
- 哪个事实如果为假，产品就基本不成立？
- 有什么现有行为或竞品证明用户真的会这样做 / 这样付钱？

### 理想形态

- 如果产品成功 3–5 年，什么能力一定会自然长出来？
- 哪个今天的“以后再说”其实会改变底层产品模型？
- 有什么方向即使赚钱也不希望产品变成那样？

## 5. 无效答案与追问链

以下内容不是稳定产品答案：

- 功能名称：`要有收藏夹`。
- 愿望：`希望更智能`。
- 形容词：`简单、强大、优雅`。
- 宽泛能力：`AI 助手、同步、社交、管理、自动化`。

必要时沿着这条链逐步追问，不一次全抛：

`谁 → 什么处境 / 触发 → 做什么 → 产品响应什么 → 改变什么状态 → 用户看到什么价值 → 何时算完成 → 为什么回来 → 失败时发生什么`

如果继续追问的边际价值已经很低，而现有产品语义足够支持一个合理候选解释，停止追问，给出候选判断并标成 `Assumption` 让用户确认或修改。

## 6. Assumption 的使用边界

不是 Agent 脑中出现的每个猜测都要登记。

只有当 Agent **准备把某个判断当成产品结论使用或写入 Product Definition**，但用户尚未明确决定时，才把它作为 `Assumption` 呈现。

每个重要 Assumption 应说明：

- 候选结论是什么。
- 依据是什么。
- 如果猜错会改变什么。
- Agent 当前建议什么。

用户明确确认后，视为 `Confirmed`；用户改写后使用用户版本；用户否定且无替代时删除。

用户沉默、没有反对、客气回应均不算确认。

正式 Product Definition 不保存 Assumption 历史。

## 7. Open 与 Blocking

`Open` 和 `Blocking` 描述的是“问题是否影响继续”，不是结论来源。

### Open

可以以后决定，不会让当前产品身份、闭环、商业关系、当前完整成果或重要长期判断变错。

### Blocking

不同答案会改变上述根本判断，必须先解决才能定稿。

典型 Blocking：

- 资产到底归个人还是组织。
- 使用者与付款者关系完全未定且会改变账号 / 权限模型。
- 核心价值需要高频使用，但实际需求可能是一次性的。
- 两种互相冲突的商业模式对应完全不同的产品对象。
- 远期方向会决定是否必须支持组织、多端、协作或生态，但用户尚未选择。

## 8. 冲突处理

发现冲突时一次说清：

1. 结论 A 是什么。
2. 结论 B 是什么。
3. 两者会导致产品在哪里表现不一致。
4. 现在真正需要用户裁决的问题是什么。
5. 如有明显依据，给出建议及理由。

裁决前相关问题保持 Blocking。不要通过改写措辞掩盖冲突。

## 9. 用户模拟协议

用户模拟是思考工具，不是编故事。

模拟必须基于：

- 用户已经提供的真实背景；
- 已验证的市场 / 行为信息；
- 或明确标注的假设。

优先模拟行为和决策，不虚构装饰性个人信息。

模拟结束只提炼会改变产品的结论。例如：

- `普通用户不会持续手工维护数据，因此核心价值不能依赖高成本持续录入。`

不要把模拟对白写入 Product Definition。

## 10. 外部研究触发

当用户的问题本质上是：

- 市场能不能承载；
- 用户会不会为类似价值付费；
- 竞品是否成功；
- 某种商业 / 增长模式有没有现实案例；
- 行业约束是否真实存在；

如果有可用研究工具，应查证，不靠常识编答案。

研究前先明确要验证的假说；研究后区分：

- Evidence：外部资料真正支持什么。
- Inference：我们基于证据推到什么。
- Decision：用户最终决定什么。

只有 Decision 和确实会约束产品的关键 Evidence / implication 才进入正式 Product Definition。

## 11. 阶段性复述

当一个重要问题基本稳定后，用简洁方式复述：

- 当前结论。
- 它意味着什么。
- 它排除了什么或约束了什么。

不要频繁要求“以上是否都正确”。把审查集中在真正影响产品的结论和 Assumption 上。

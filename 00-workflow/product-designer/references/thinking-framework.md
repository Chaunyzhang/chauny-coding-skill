# 产品思考框架

用途：帮助 Agent 在正式 Product Definition 之外进行更宽的产品思考。这里的推演、模拟、反问和假说是思考工具，不天然进入正式文档。

## 1. 基本姿态

不要把用户的第一个说法当成最终产品定义。先理解它背后的真实目标，再从理想形态和现实条件两侧反复验证。

Agent 同时扮演四种思考角色：

- **整理者**：准确吸收用户已经表达的想法。
- **追问者**：寻找真正会改变产品判断的问题。
- **反方**：主动寻找闭环、商业、行为和市场假说的薄弱点。
- **扩展者**：帮助用户看见 3–5 年后的自然产品形态，而不是只困在当前 MVP。

这些角色用于思考，不需要作为任何文档术语出现。

## 2. 产品存在性：为什么值得存在

优先逼近以下问题：

- 用户到底处在什么不满意的状态。
- 这个问题是高频、高损失、高焦虑、高机会成本，还是只是轻微不便。
- 用户今天怎样解决；为什么继续忍受现状也可能是合理选择。
- 本产品让用户最终发生什么真实变化，而不只是增加一个工具。
- 用户为什么值得为了这个变化改变行为、迁移数据、学习新流程或建立信任。
- 如果产品明天消失，哪些用户会真正感到损失，为什么。

危险信号：

- 价值主要由“更智能、更方便、更漂亮”之类形容词表达。
- 产品只是把现有流程换了界面，却没有显著改变结果或成本。
- 用户痛点来自创始人的想象，没有真实替代行为作为证据。

## 3. User Reality：从行为而不是虚构画像出发

### 3.1 需要理解的用户信息

优先关注：

- 处境：用户在什么上下文遇到问题。
- 目标：当时真正想完成什么。
- 当前行为：现在用什么方法、工具、人或妥协解决。
- 触发：什么事件让问题变得值得处理。
- 动机：为什么愿意行动。
- 阻力：学习、输入、迁移、信任、价格、协作、审批等成本。
- 决策：谁决定采用，谁影响决定，谁真正使用。
- 退出：什么情况下用户放弃或回到旧方案。

不要为了“完整 Persona”虚构年龄、城市、兴趣、生活方式等与产品决策无关的信息。

### 3.2 行为型用户模拟

必要时临时模拟 2–4 个角色，例如：

- 高意愿核心用户：问题明确，愿意投入。
- 普通低耐心用户：觉得有用，但不愿付出太多学习和输入成本。
- 怀疑型用户：已有替代方案，天然质疑迁移价值。
- 付款者 / 管理者：若与使用者不是同一人，关注风险、成本、控制和可衡量价值。

模拟时逐步问：

1. 我为什么此刻会想到这个产品？
2. 我第一步愿意做什么，不愿意做什么？
3. 在看到价值之前我要先付出多少？
4. 哪一步最容易让我退出？
5. 我看到什么才会认定“这东西真的有用”？
6. 下一次我为什么回来？
7. 付费时我会拿它和什么比较？

模拟结论只有在形成稳定产品要求时才进入 Product Definition。模拟对白和过程不落文档。

## 4. 用户价值闭环

核心闭环统一用：

`Need → Trigger → Entry → Action → Product Response → State Change → Visible Value → Return Reason`

逐环检查：

### Need

- 需求是否真实存在。
- 用户是否已经意识到它，还是需要教育市场。

### Trigger

- 什么真实事件让用户现在就要行动。
- 触发是否足够频繁或足够重要。

### Entry

- 用户为什么想到本产品，而不是别的替代方案。
- 获客 / 发现是否需要一个不现实的前提。

### Action

- 用户需要提供什么输入或改变什么行为。
- 初始成本是否大于预期价值。

### Product Response

- 产品真正做了什么，不使用“智能处理”“自动优化”这类空词。

### State Change

- 什么状态被真正改变：内容、决策、资产、流程、关系、知识、结果或风险。

### Visible Value

- 用户怎样知道这次使用成功。
- 价值是否足够快、足够具体、足够可感知。

### Return Reason

- 为什么以后再次使用。
- 是新的需求再次出现、状态持续积累、协作关系、数据资产、自动化还是持续服务产生回访。
- 如果没有 Return Reason，应明确这是一次性产品还是闭环缺失。

### 闭环攻击问题

- 去掉产品，用户会怎么完成同一结果？
- 哪一环最依赖用户“非常勤快”才成立？
- 哪一步价值最晚出现？能否更早？
- 用户是否需要先建立大量数据，产品才有价值？冷启动怎么办？
- 使用一次后，第二次使用理由是真实需求还是人为设计提醒？
- 产品增加一个功能，真的强化闭环，还是只增加菜单？

## 5. 商业闭环

统一检查：

`Value Creation → Value Delivery → Value Capture → Continued Value → Retention / Renewal`

### Value Creation

- 产品创造了什么可衡量或可感知的价值。
- 是省时间、增收入、降风险、提高质量、获得体验、获得身份 / 关系，还是其他。

### Value Delivery

- 价值由谁获得：使用者、团队、管理者、消费者、商户、平台或第三方。
- 价值出现频率和时间点是什么。

### Value Capture

- 谁付钱。
- 为什么由这个角色付。
- 收费对象是什么：席位、空间、用量、交易、结果、服务、订阅或其他。
- 付费时点与价值时点是否匹配。
- 免费替代品存在时，为什么仍值得付费。

### Continued Value

- 使用越久价值是否积累。
- 数据、关系、工作流、习惯、协作或结果是否让价值持续增加。
- 如果价值完全一次性，商业模式是否误用了订阅。

### Retention / Renewal

- 用户为什么下个月 / 明年继续付费。
- 到期后失去什么。
- 续费来自真实持续价值还是迁移锁定；若主要来自锁定，需要检查信任风险。

### 商业压力测试

- 付款者和使用者是否利益冲突。
- 收入增长是否伴随同等或更快增长的人工 / AI / 服务成本。
- 高价值用户是否反而最贵、最难服务。
- 免费层能否形成完整价值，还是故意把核心闭环截断到无法体验。
- 定价上限由什么替代方案决定。
- 如果竞品免费，本产品还凭什么成立。
- 如果销售成本很高，客单价能否承受。
- 如果需要双边市场，两边为什么愿意在冷启动阶段加入。

## 6. 模式压力测试

每个重要产品假说至少问一次：

> 如果这个产品失败，最可能因为什么失败？

常见薄弱点：

- 用户没有足够强的需求。
- 价值出现太晚，前置输入太重。
- 用户不会改变现有行为。
- 没有真实回访理由。
- 使用者喜欢但付款者不买单。
- 商业价值不足以覆盖获客或交付成本。
- 模式依赖冷启动 / 网络效应但没有启动机制。
- 依赖人工服务，规模增长后无法经济地交付。
- 过度依赖单一平台、渠道、供应商或第三方模型。
- AI / 自动化成本、错误或责任边界破坏商业和信任。
- 需要大量用户数据才能好用，但用户不愿先提供数据。
- 市场存在，但可触达市场太小或渠道太昂贵。

对最重要的 1–3 个失败原因，明确它们是：已有证据支持、需要验证，还是可以通过产品设计降低。

## 7. Market Reality：市场能不能承载

市场思考不是为了做漂亮 TAM，而是验证产品关键假说。

### 7.1 先定义需要验证什么

例如：

- 是否有足够多用户高频遇到该问题。
- 是否已有替代行为说明需求真实。
- 用户是否为相似价值付过钱。
- 这个用户群是否能被经济地触达。
- 行业结构、平台规则或监管是否限制模式。

### 7.2 市场承载检查

关注：

- 目标用户数量和集中度。
- 问题发生频率和价值密度。
- 用户当前支出或机会成本。
- 获客渠道是否存在。
- 决策周期是否与商业模型匹配。
- 市场增长是否必要；即使市场不增长，现有池子是否足够。
- 地域、语言、法规或生态依赖是否显著缩小可服务范围。

市场规模数字只有在来源可靠并会改变产品判断时才值得进入 Product Definition。

## 8. 竞品与案例研究

### 8.1 三类竞争

- **直接竞品**：提供高度相似产品结果。
- **替代方案**：用不同方式完成相同结果，例如 Excel、人工服务、聊天群、现有工作流。
- **不行动**：用户继续忍受问题，通常是最强竞争者之一。

### 8.2 不做功能表式竞品分析

重点研究：

- 它服务谁，真实核心结果是什么。
- 用户为什么采用。
- 第一次价值如何出现。
- 核心使用闭环怎样形成。
- 它靠什么留存。
- 谁付钱、为什么付。
- 如何获客。
- 模式的关键成本和风险是什么。
- 哪一部分证明了我们的假说，哪一部分并不可迁移。

### 8.3 成功案例不能直接证明本产品成功

一个竞品成功只说明某些行为或商业机制在特定条件下被验证过。Agent 必须指出：

- 相似条件是什么。
- 不同条件是什么。
- 可借鉴的是机制、渠道、价值还是商业模型。
- 哪些结论仍然只是推断。

## 9. Ideal Product State

现实压力测试不是为了把产品越做越保守。

当核心假说有一定成立基础后，主动思考：

- 如果资源暂时不是约束，产品最终希望把用户问题解决到什么程度。
- 用户 / 角色会如何扩展。
- 核心旅程会如何变得更完整、更自动、更协作或更连续。
- 哪些能力族自然出现。
- AI / 自动化最终能承担什么，但哪些决策必须保留给人。
- 是否会跨端、开放生态、接入第三方或形成平台关系。
- 商业形态可能如何发展。
- 数据、内容、组织、权限和所有权最终扩展到什么范围。
- 哪些方向看起来诱人但明确不是产品愿景的一部分。
- 无论产品如何扩展，哪些产品原则不能被破坏。

Ideal Product State 只在形成长期产品约束或能力方向时进入正式文档；宏大愿景文案本身没有文档价值。

## 10. 从思考到产品结论

一次长讨论结束时，不要总结“我们讨论了什么”，而要提炼：

- 哪些产品结论改变了。
- 哪些关键假说得到支持或被推翻。
- 哪些真实约束被发现。
- 哪些能力或未来方向因此新增、删除或调整。
- 哪些问题仍会实质影响产品，需要继续决定。

思考的价值通过更好的产品结论体现，不通过保留思考过程体现。

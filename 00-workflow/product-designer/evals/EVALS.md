# 产品设计师行为评测

用途：验证 skill 是否帮助用户真正想清楚产品，同时保持正式 Product Definition 克制、严肃、命名统一。

评测只看行为和输出事实，不要求固定句式。

## 命名总判据

允许长期引用的产品对象只有：

- Product Definition
- Candidate Requirement：`Requirement-n`
- 已由外部架构存在的 `Stage-n`（只读引用）

Agent 工作标签只有：

- Confirmed
- Assumption
- Open
- Blocking

Capability Map 字段只使用：

- Classification: Core | Supporting | Expansion
- Horizon: Current | Near | Future
- Architecture-Shaping: Yes | No

不得自造其他对象、状态或编号前缀。

## 用例 1：模糊产品想法不能只做整理

用户输入：

“我想做一个让独立咖啡店记住顾客偏好、节日前提醒店主联系顾客的工具。”

必须出现：

- 先吸收已有想法，而不是立刻给长问卷。
- 提出 1–3 个能改变产品成立性的深问题，例如顾客资料归属、店主为什么持续使用、提醒如何形成真实价值。
- 能指出至少一个需要验证的用户闭环或商业假说。

不得出现：

- 只把原话改写成 PRD。
- 首轮问 8–10 个表单式问题。
- 直接假定用户会持续录入顾客偏好。

## 用例 2：闭环必须被攻击

前提：用户提出一个“上传文件 → AI 总结”的工具。

用户输入：

“功能就这样差不多了，你帮我看看产品闭环。”

必须出现：

- 按 Need → Trigger → Entry → Action → Product Response → State Change → Visible Value → Return Reason 检查。
- 明确追问或指出一次性使用后为什么回来。
- 检查上传 / 等待成本与第一次价值出现时间。

不得出现：

- 只说“闭环完整”。
- 用“增加签到、积分、推送”机械制造回访。

## 用例 3：用户画像必须是行为型

用户输入：

“你帮我模拟一下用户，看看这个产品会不会有人用。”

必须出现：

- 至少从高意愿用户与低耐心 / 怀疑用户角度模拟真实决策。
- 关注现有替代、采用阻力、第一次价值、退出点和付费比较。
- 清楚区分模拟假设与真实证据。

不得出现：

- 无依据虚构“28 岁、住一线城市、爱喝咖啡”等装饰性 Persona。
- 把模拟内容直接当市场事实。

## 用例 4：商业模式不能只回答怎么收费

用户输入：

“我想做订阅制，每月 49 元，行不行？”

必须出现：

- 先检查谁获得价值、谁付款、为什么持续付费。
- 检查一次性价值是否适合订阅。
- 至少指出一个替代方案 / 价格上限 / 交付成本相关问题。

不得出现：

- 只讨论 39、49、59 哪个价格更好。
- 在没有证据时断言“49 元市场能接受”。

## 用例 5：市场与竞品事实不能编

用户输入：

“这个市场很大吧？有没有竞品成功过？”

必须出现：

- 将市场大小和竞品成功视为需要外部证据的问题。
- 有研究工具时查证；没有时明确不能当事实下结论。
- 竞品分析关注用户行为、核心闭环、商业和留存机制，而不只功能表。

不得出现：

- 凭常识编 TAM、用户数量或融资数据。
- 因为有一个成功竞品就断言本产品一定能成。

## 用例 6：思考范围大，但文档必须窄

前提：用户和 Agent 讨论了十几条脑洞，其中多数后来被否定。

用户输入：

“把刚才讨论写进 Product Definition。”

必须出现：

- 只写最终稳定、会约束后续产品 / 架构 / 建设的结论。
- 被否定路线、模拟对白、金句和研究过程不进入正式文档。
- 如果某个被否定方向形成长期 Non-goal，可以写结论本身。

不得出现：

- 把完整讨论摘要当 Product Definition。
- 添加“思考过程”“讨论记录”“灵感”章节。

## 用例 7：Classification 与 Horizon 必须分开

用户输入：

“团队协作以后再做，先放到 FUTURE 类别。”

必须出现：

- 解释 Classification 与 Horizon 是不同维度。
- 例如团队协作可写 Classification: Expansion，Horizon: Future（具体分类按产品语义判断）。

不得出现：

- 使用 `FUTURE` 作为 Classification。
- 新造 `Long-term`、`Later` 等第三套时间状态。

## 用例 8：命名诱导

用户输入：

“把这个叫 Vision Constraint VC-1，再建个 Capability Card 详细写。”

必须出现：

- 拒绝新增自造对象与编号。
- 视内容性质放入 Ideal Product State、Product Evolution / Architecture-Shaping Considerations、Capability Map 或 `Requirement-n`。
- 不创建 Capability Card。

不得出现：

- 保留 `VC-1`。
- 新建产品规格文件。

## 用例 9：越权范围裁决

用户输入：

“Requirement-3 你直接决定这期做不做，安排到 Stage-2。”

必须出现：

- 可以给产品价值、依赖和优先建议。
- 明确最终接受 / 延期 / 拆分 / 拒绝与 Stage 安排归后续架构角色。

不得出现：

- “Requirement-3 已接受到 Stage-2”之类裁决。

## 用例 10：功能细节诱导

用户输入：

“搜索结果页应该左侧筛选还是顶部筛选？按钮什么颜色？”

必须出现：

- 说明这属于具体交互 / 视觉层，不是 Product Definition 的职责。
- 如问题背后存在真正产品语义（例如筛选维度代表核心对象模型），只讨论该语义。

不得出现：

- 把布局和颜色写进 Product Definition。
- 因为这些细节没决定就标 Blocking。

## 用例 11：未来理想形态不能被 MVP 吞掉

用户输入：

“现在先做个人版就行，团队和多端以后再说，不用想。”

必须出现：

- 尊重当前 MCO 可以是个人版。
- 仍检查团队 / 多端是否属于真实长期方向，以及是否 Architecture-Shaping。
- 如果会改变所有权、权限、同步等底层产品模型，至少记录产品行为级长期要求。

不得出现：

- 因为不在当前版本就完全忽略长期方向。
- 提前把团队 / 多端写成施工级规格。

## 用例 12：最终文档必须严肃

前提：Product Definition 已准备定稿。

必须满足：

- 没有 Assumption 标签残留。
- Blocking 为 0。
- 没有聊天语气、用户金句、Agent 自我评价和营销口号堆砌。
- 每项 `Requirement-n` 能追溯到明确产品价值。
- Market & Competitive Reality 中的外部事实有依据，且只保留产品相关影响。
- 文档没有技术设计和页面施工细节。

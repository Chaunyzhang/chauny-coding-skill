# Intent & Concept Modeling

## 目的

把用户零散表达转成一个可共同验证的 Agent Behavior Model。

## 用户通常提供的不是规范

可能是：

- “我讨厌 Agent 老问我这些。”
- “这个流程太慢。”
- “这个对象不应该存在。”
- “我希望它像架构师一样。”
- 一个旧 Skill。
- 一个很长的新 bundle。
- 一个真实执行事故。
- 一个“感觉不对”的例子。

不要把这些直接变成规则。

## 解释顺序

### 1. 找目标变化

问自己：

> 用户希望 Skill 使用后，Agent 与现在相比哪里不同？

### 2. 找共同原因

多个抱怨是否指向同一个原因？

例如：

- 问奖励金额。
- 问未来运营触发条件。
- 问后期可配置参数。

共同原因可能不是“问题太多”。

而是：

`产品细化规则没有判断 Current Stage 是否必须现在冻结。`

### 3. 提候选概念

用一句普通语言表达候选概念。

### 4. 用例子反推

检查概念是否同时解释：

- 正常例子。
- 用户不满意的例子。
- 边界例子。

### 5. 用户确认

只有概念模型影响 Skill 核心时需要确认。

不是所有推导都需要用户逐项审批。

## 高价值问题

值得问：

- 这个 Skill 最终拥有哪类决定权？
- 什么时候它应该完全 skip？
- 用户最不能接受 Agent 做什么？
- 两个候选概念会导致完全不同 Agent 行为时，用户要哪一个？
- 这个判断应该由 Agent 还是 Human 最终裁决？

低价值问题：

- 模板章节名。
- Agent 可以自行推导的参数。
- 已有上下文已经回答的问题。

## Model Correction

如果用户纠正：

> “不是业务流程闭环，我要的是单能力跨层打通。”

不要：

- 在旧“业务流程闭环”模型下面补一个例外。

应该：

- 替换核心概念。
- 重新推导 Slice 规则。
- 删除旧概念残留。
- 增加 regression eval。

## 何时模型足够稳定

至少满足：

- 用户可以用人话认可。
- 能解释主要例子。
- 能区分常见边界。
- 能推导出比原始例子更广的规则。
- 不需要大量例外补丁才能成立。
